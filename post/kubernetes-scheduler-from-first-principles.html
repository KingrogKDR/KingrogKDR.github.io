Understanding the Kubernetes Scheduler Framework

April 1, 2026 · 7 min read

In my previous post, I discussed the need for a custom Kubernetes Scheduler.

There are a lot of resources on directly implementing a custom scheduler. But I decided to jump to its foundations first. I read the Kubernetes scheduling framework and wanted to share what I learnt and discovered.

This post breaks down the Kubernetes Scheduler Framework by reconstructing its core ideas from first principles.

The core idea

At a high level, scheduling is just a decision pipeline.

  1. Pick a node from the filtered list
  2. Assign the pod to that node

These correspond to two phases.

  • Scheduling Cycle: decide which node should run the Pod.
  • Binding Cycle: assign the Pod to that node.

Together, they form the scheduling context.

The three building blocks

To customize scheduling, Kubernetes exposes three key concepts.

Extension Points: These are hooks in the scheduling pipeline where logic can be injected.

Examples include Filter, Score, and Bind.

These are points or stages in the scheduling pipeline where we can inject our own logic.

Plugins: These are the actual implementations of scheduling logic.

Examples include preferring nodes with more CPU or balanced usage.

We can think of these as the logic that we want to implement. These are tests that the nodes have to go through to be selected.

Interfaces: These define the contracts or methods that plugins must implement.

For example, a ScorePlugin must implement a Score method.

So, these are methods that plugins use to select the nodes. A single plugin can use multiple interfaces/methods.

Building a minimal scheduler

To understand how these concepts work together, I tried implementing them into a small scheduler.

Scoring plugins

I implemented two scoring strategies.

CPU Plugin: prefers nodes with more free CPU.

go 
type CPU struct{}

func (c *CPU) Name() string {
    return "CPUScore"
}

func (c *CPU) Score(node Node, pod Pod) int {
    free := node.noOfCPUs - node.usedCPUs
    return free
}
Scores nodes based on available free CPU.

Balanced Usage Plugin: prefers nodes close to 50% utilization.

go 
type BalancedUsage struct{}

func (b *BalancedUsage) Name() string {
    return "BalancedUsage"
}

func (b *BalancedUsage) Score(node Node, pod Pod) int {
    usageRatio := float64(node.usedCPUs) / float64(node.noOfCPUs)

    diff := usageRatio - 0.5
    if diff < 0 {
        diff = -diff
    }

    return int((1 - diff) * 100)
}
Scores nodes based on how close CPU usage is to an optimal balanced state (50%).

This avoids both overload and underutilization.

Weighted plugins

Not all policies are equally important.

So, I assigned a weight to each plugin, and final scores are computed as a weighted sum.

totalScore += pluginScore * weight

This allows one policy to dominate over others.

Scheduling logic

go 
func schedule(nodes []Node, pod Pod, plugins []WeightedPlugin) Node {
    bestScore := -1
    var bestNode Node

    for _, node := range nodes {
        totalScore := 0

        for _, wp := range plugins {
            score := wp.plugin.Score(node, pod)
            totalScore += score * wp.weight
        }

        if totalScore > bestScore {
            bestScore = totalScore
            bestNode = node
        }
    }

    return bestNode
}

The scheduler iterates over all nodes, computes a total score using all plugins, and selects the node with the highest score.

This is effectively the Score extension point in action.

Each plugin runs independently, and the scheduler aggregates their outputs.

To better understand how scheduling decisions change, I added multiple scenarios and printed detailed outputs for each node.

go 
func runScenario(title string, nodes []Node, pod Pod, plugins []WeightedPlugin) {
    println("\n---", title, "---")

    // Print detailed scoring
    for _, node := range nodes {
        totalScore := 0
        println("Node:", node.name)

        for _, wp := range plugins {
            score := wp.plugin.Score(node, pod)
            weighted := score * wp.weight

            println("  Plugin:", wp.plugin.Name(),
                "Raw:", score,
                "Weight:", wp.weight,
                "Weighted:", weighted)

            totalScore += weighted
        }

        println("  Total Score:", totalScore)
    }

    // Use schedule function for final decision
    best := schedule(nodes, pod, plugins)
    println("=> Selected Node:", best.name)
}

This function runs multiple scheduling scenarios, prints per-plugin contributions, and shows how weighted scores determine the final node selection.

What this demonstrates

  • Policy tradeoffs: Different weights lead to different scheduling outcomes.
  • Sensitivity: Small changes in weights can drastically change decisions.
  • Missing constraints: Without a Filter phase, invalid nodes are still considered.
  • Real-world complexity: Highlights the need for normalization and constraint enforcement.

Key insights

Scheduling is optimization, not mandatory

From what I learnt, we can argue that pods can still run on nodes without a scheduler. It can be assigned to any random node at any moment. But to make sure, it runs efficiently and reliably, scheduler is important.

Weights change behavior drastically

Increasing a plugin’s weight can completely dominate scheduling decisions. It can make or break plugins. Different plugins may return scores/values in different ranges (e.g., 2–6 vs 0–100). This leads to imbalance. Normalization of scores can ensure fairness across plugins.

Plugins are independent

Each plugin operates in isolation. The scheduler is responsible for combining the results.

Mapping to real Kubernetes

ScorePlugin → Plugin

Score() → Score extension point

WeightedPlugin → Plugin weighting

schedule() → Scheduling cycle

Conclusion

If we strip Kubernetes scheduling to its essence:

  1. Filter: remove invalid nodes
  2. Score: rank valid nodes
  3. Bind: assign the pod

Everything else is an optimization layer on top.
